## 1. วัตถุประสงค์

จำลองการทำงานของพนักงานเก็บเงิน 1 คน ตั้งแต่เปิดเครื่อง เข้ากะ รับรถทุกประเภท ทุกวิธีชำระ ขายคูปอง จัดการกรณีผิดปกติ ช่วงรถหนาแน่น จนถึงปิดกะและเข้าโหมดช่าง เพื่อยืนยันว่า

1. ทุกฟังก์ชันใช้งานได้จากคีย์บอร์ด Cherry (เส้นทางเดียวกับคีย์บอร์ด USB จริง)
2. รายการที่เกิดขึ้นถูกส่งครบทั้ง **Sup Adjust** และ **DC (RabbitMQ)** ตรงตามจำนวนและประเภทการชำระ
3. การขายคูปองถูกบันทึกและแจ้ง **TA Web Service** ครบทุกใบ และบั๊กที่แก้ใน 2.0.4 ไม่กลับมา
4. โปรแกรม **ไม่ดับ ไม่ค้าง** ตลอดกะ (ตรวจจำนวนครั้งที่ process ถูก start ใหม่ + การตอบสนองต่อคีย์ทุกขั้น + หน่วยความจำ)
5. ไม่มี Exception/Error ใหม่ใน log ของ TCT

## 2. เงื่อนไขก่อนเริ่ม

- `./sim.sh start` แล้ว แผงควบคุมแสดงสถานะ TCT / RTO / Sup Adjust / DC เชื่อมต่อครบ
- EDC จำลองอยู่โหมด `approve`, QR = `paid`; TA จำลองโหมด `ok`; คูปองคงเหลือชนิด 35 และ 80 อย่างน้อยชนิดละ 5 ใบ
- ใบเสร็จพิมพ์ลงไฟล์ `/tmp/printer.out` ในเครื่องจำลอง (ดูได้จาก log `PrintReceipt`/`PrintSalesCoupon : sent`)
- ชื่อปุ่มในตาราง = ชื่อบนคีย์บอร์ด Cherry; `[1]`…`[9]` = แป้นตัวเลข; "รถผ่าน" = รถวิ่งผ่าน Loop → OB แล้ว AVC ส่งประเภทรถ (สคริปต์ใช้ scenario `normal` + AVC)

## 4. เกณฑ์ผ่าน (Pass criteria)

1. รายการรถที่ Sup Adjust ได้ = DC ได้ = จำนวนที่คาด (**รวม 50 รายการ**) และวิธีชำระ/ประเภทรถตรงทุกขั้นที่ระบุ
2. TA ได้ `SoldCoupon` **รวม 7 ใบ** (D1=1, D2=3, D3=1, D4=1, D5=1) และ D6 ไม่ขาย
3. EDC ได้คำขอชำระบัตรตามจำนวนที่คาด (D3 = 1 ครั้ง)
4. TCT ไม่ถูก start ใหม่ระหว่างกะ (crash = 0) และทุกขั้นมี log การรับคีย์ (ไม่ค้าง)
5. ไม่มีบรรทัด `Exception` / `- Error` ใหม่ใน log ยกเว้นที่คาดไว้ (EDC ปฏิเสธ/ไม่ตอบ, QR ยังไม่ชำระ, TA ช้า)
6. หน่วยความจำ mono ไม่โตผิดปกติ (< +50 MB จากต้นกะ)
